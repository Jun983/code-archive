    Codex 자동화 실습¶

    ← 디자인 시스템으로 돌아가기

    샘플 Figma 파일만 만든 상태에서 시작해, Figma 정리부터 개발 전달까지를 Codex의 skill 4개로 진행하면서 정해 둔 지점마다 사람이 승인합니다. 선택 실습입니다.

    구분 내용
    입력 샘플 파일 5-2단계까지 마친 Figma 파일, 디스코드에서 받은 .agents 압축 파일
    산출물 정리한 Figma 사본, design-system-practice-auto 안의 ds-spec.json·토큰·컴포넌트 라이브러리·전달 묶음
    선행 단계 샘플 Figma 파일. 수동 실습의 결과는 쓰지 않습니다.

    시나리오¶

    상황¶

    샘플 파일은 색상·간격·모서리 반경·글자 속성을 직접 입력한 상태입니다. 변수, 스타일, 토큰 파일, 컴포넌트 코드는 하나도 없습니다. 실습자는 이 파일을 React 개발자에게 전달할 수 있는 상태로 만들어야 하며, 작업은 Codex에게 맡기고 자신은 검토자가 됩니다. 전달을 마친 뒤에는 사본의 색상 값 하나를 바꾸고, 전용 skill 없이 프롬프트로 요청해 새 버전을 다시 전달합니다.

    시작 상태¶

    샘플 파일 절차를 그대로 따랐다면 파일에는 아래 값이 있습니다. 정리 전과 후를 비교하는 기준이므로 시작하기 전에 확인합니다.

    대상 색상 간격·모서리 반경·크기 글자(Inter)
    Button 배경 3B82F6, 글자 FFFFFF 패딩 세로 10·가로 12, 반경 6, 크기 65 × 41 Medium 14
    Input default 배경 FFFFFF, 선 D1D5DB, 글자 9CA3AF 패딩 세로 10·가로 13, 반경 7, 크기 240 × 40, 선 두께 1 Regular 14
    Input focus 선 3B82F6, 나머지는 default와 같음 default와 같음 default와 같음
    Input error 선 EF4444, 나머지는 default와 같음 default와 같음 default와 같음
    Card 배경 FFFFFF, 선 E5E7EB, 글자는 기본 검정 000000 패딩 16, 간격 8, 반경 12, 크기 280 × 78, 선 두께 1 제목 Medium 16, 본문 Regular 14
    • Examples 페이지에는 세 컴포넌트의 인스턴스가 하나씩 있습니다.
    • Cover 페이지의 텍스트 두 개(Medium 32, Regular 16)는 컴포넌트가 아닙니다.

    목표 상태¶

    산출물 완료 상태
    Figma 사본 컴포넌트의 색상·간격·반경이 변수에, 글자가 텍스트 스타일에 연결돼 있고, 승인한 변화 말고는 겉모습이 같습니다.
    ds-spec.json 승인한 설계가 담겨 있고 status가 confirmed입니다.
    tokens/tokens.json, build/css/variables.css 변수의 이름·값·참조가 ds-spec.json과 같습니다.
    my-ui, consumer 라이브러리가 빌드되고, 다른 프로젝트에 설치해 타입 검사와 빌드가 됩니다.
    handoff 토큰 파일과 my-ui-0.1.1.tgz가 있고, 바꾼 색상 값이 새 패키지에 반영돼 있습니다.

    진행 흐름¶

    단계 skill Codex가 맡는 일 사람이 직접 하는 일 다음 단계로 넘기는 것
    1. 환경 준비 없음 연결 확인 호출 도구 설치, 폴더 준비 작업 폴더, 원본 파일과 사본
    2. Figma 정리 ds-figma-organize 분석, 설계안 제안, Figma 정리, ds-spec.json 확정 설계안 검토, 화면 확인 ds-spec.json, 정리한 사본
    3. 토큰 추출·변환 ds-design-tokens 변수 추출, 변환, 대조 대조 결과 확인 tokens.json, variables.css, build-tokens.js
    4. 컴포넌트 라이브러리 ds-component-library 코드 설계와 작성, 빌드, 사용 확인 코드 설계 검토, 카탈로그 화면 확인 my-ui, consumer
    5. 개발 전달과 색상 변경 전달은 ds-handoff, 색상 변경은 프롬프트 산출물 모으기, 문서 작성, 검사, 패키징, 변경 절차 구성과 반영 전달 내용 검토, Figma 색상 변경, 변경 계획 검토 handoff

    판단 기준¶

    • 컬렉션·변수·스타일·레이어의 구조와 이름은 정해진 답이 없습니다. 사용자의 요청, 파일에 이미 있는 규칙, Codex의 판단 순서로 정합니다. 샘플 파일에는 기존 변수와 스타일이 없으므로, 따로 요청하지 않으면 Codex가 근거를 붙여 제안합니다.
    • 승인한 설계는 ds-spec.json에 저장되고, 3~5단계는 이 파일을 기준으로 진행합니다.
    • 값은 Figma 파일에서 읽은 것을 씁니다. 5단계의 색상 변경도 사본을 먼저 바꾼 뒤 그 값을 읽습니다.
    • 비교할 정답 파일이 없습니다. 값은 시작 상태의 표와 원본 파일로, 형식과 참조는 검사 명령으로, 화면은 눈으로 확인합니다.
    • 각 단계의 산출물이 다음 단계의 입력이 됩니다. 승인하지 않은 단계의 결과는 다음 단계로 넘기지 않습니다.
    • 자동화 대상의 범위는 AI 자동화 도구로 줄일 수 있는 범위에서 다룹니다.

    승인 방식¶

    승인 규칙은 skill에 들어 있어 따로 보내지 않습니다. 주요 규칙은 아래와 같습니다.

    • Codex는 시작하기 전에 할 일과 바뀔 대상을 보여주고 기다립니다.
    • 승인이라고 답하기 전에는 승인 지점을 넘어가지 않습니다. 한 번의 승인은 다음 승인 지점까지만 유효합니다.
    • 승인 지점마다 바꾼 내용, 실행한 명령과 출력, 실패한 항목을 보여줍니다.
    • 결과가 기준과 다르면 임의로 고치지 않고 차이를 알립니다.
    • 직접 확인하지 못한 항목은 통과로 표시하지 않습니다.

    승인 지점에서는 아래 셋 중 하나로 답합니다.

    상황 답하는 방법
    확인할 것이 모두 맞음 승인
    바꾸고 싶은 것이 있음 승인이라고 쓰지 않고, 바꿀 대상과 원하는 결과를 적습니다. 고친 제안을 다시 검토합니다.
    보여준 내용만으로 판단할 수 없음 승인하지 않고 근거를 묻습니다. 예: 이 값을 어느 레이어에서 읽었는지 보여줘.

    1. 환경 준비¶

    환경 구성의 1~2단계를 이미 마쳤다면 1-3과 1-4는 건너뜁니다.

    1-1. 도구와 요금제 확인¶

    1. 작업: 터미널에서 Node.js와 npm의 버전을 확인합니다. 설치 방법은 개발환경 준비에서 다룹니다.

      실행 위치: 임의의 폴더

      명령어

      1
      node -v && npm -v

      출력 결과: 버전 두 줄이 나옵니다. 숫자는 환경마다 다릅니다.

    2. 기대 결과: Node.js가 22.12.0 이상입니다. skill의 기준 버전은 22.22.2입니다.

    3. 확인 방법: 첫 줄의 버전을 비교합니다.

    Figma MCP 서버의 use_figma 도구는 Figma 파일을 수정할 수 있으며, 2단계와 3단계의 skill이 사용합니다. 아래 조건은 Write to canvas를 기준으로 합니다.

    • 원격 서버에 연결한 클라이언트에서 쓰며, Codex는 지원 클라이언트에 포함됩니다.
    • 대상 요금제는 Professional, Education, Organization, Enterprise이고 파일 편집 권한이 필요합니다. Starter(무료) 요금제는 대상에 없으므로, 해당하면 이 선택 실습을 건너뜁니다.
    • 베타 기능입니다. 베타 기간에는 무료이며, 이후 사용량 기반 유료 기능이 될 예정입니다.
    • 읽기 도구에는 호출 제한이 있습니다. 조건은 Rate limits and access에서 확인합니다.

    1-2. 원본 보관과 사본 준비¶

    1. 작업: 샘플 파일 5-2단계까지 마친 파일을 Figma에서 복제하고, 사본의 이름에 Codex를 덧붙입니다. 사본의 파일 링크를 복사해 둡니다.
    2. 기대 결과: 수정하지 않을 원본과 Codex가 정리할 사본이 따로 있습니다.

    3. 확인 방법: 사본을 열어 Cover, Components, Examples 페이지와 시작 상태의 값을 확인합니다.

    4. 원본은 2단계 이후 겉모습을 비교하는 기준이므로 편집하지 않습니다.

    5. 직접 만든 다른 Figma 파일의 사본도 쓸 수 있습니다. 다만 아래 제약을 벗어나면 Codex가 알리고 멈춥니다. 시작 상태의 표와 이 문서의 예상 내용은 샘플 파일에만 해당합니다.
    제약 내용
    변수 타입 Color와 Number만 씁니다. Number는 px 길이에만 씁니다.
    모드와 색 컬렉션마다 모드는 하나이고, 색에 투명도를 쓰지 않습니다.
    이름 소문자·숫자·-로 쓰고 계층은 /로 나눕니다. 컬렉션이 달라도 겹치지 않아야 하며, 한 이름이 다른 이름의 상위 경로가 되면 안 됩니다.
    참조 같은 파일의 같은 타입 변수만 가리킵니다.

    1-3. Figma 플러그인 연결¶

    1. 작업: Codex 앱의 Plugins 화면에서 Figma를 설치하고, Figma MCP 서버 연결의 Codex 앱 방식에 따라 접근을 허용합니다. 새 대화에 아래 프롬프트를 보냅니다.

      프롬프트
      1
      Figma MCP의 whoami를 호출해 요금제와 시트를 알려줘. 호출에 실패하면 추측 없이 오류 메시지를 그대로 알려줘.

    2. 기대 결과: 요금제가 1-1의 대상에 해당합니다.

    3. 확인 방법: 응답 위의 Worked for … 를 펼쳐 Figma 도구를 호출했는지 확인합니다. 호출한 흔적이 없으면 응답을 결과로 인정하지 않습니다.

    1-4. 작업 폴더와 skill 준비¶

    1. 작업: 디스코드에서 압축 파일을 내려받고, 작업 폴더를 둘 위치에서 아래 명령을 실행합니다. <받은 압축 파일 경로>는 내려받은 파일의 경로로 바꿉니다.

      실행 위치: 작업 폴더를 둘 위치

      명령어

      1
      mkdir design-system-practice-auto && unzip -q "<받은 압축 파일 경로>" -d design-system-practice-auto && ls design-system-practice-auto/.agents/skills

      출력 결과

      1
2
3
4
      ds-component-library
ds-design-tokens
ds-figma-organize
ds-handoff

    2. 기대 결과: Codex 앱에서 design-system-practice-auto 폴더를 열고 새 대화의 입력창에 $ds를 입력하면, skill 4개가 Project 표시와 함께 나옵니다. 목록에는 ds-handoff가 Ds Handoff처럼 표시됩니다.

    3. 확인 방법: 이름 4개를 위 출력과 대조하고, 입력한 $ds는 지웁니다. 2~5단계의 프롬프트는 이 대화에서 이어 보냅니다.

    3. 확인 방법: handoff 폴더가 아직 만들어지지 않았는지 확인하고 승인이라고 답합니다.

    5-2. 첫 전달 승인¶

    1. 작업: Codex가 멈출 때마다 아래 항목을 확인하고 승인이라고 답합니다.

      승인 지점 확인할 것
      산출물 모으기 handoff/tokens에 tokens.json과 variables.css가 있는지
      사용 가이드와 패키지 my-ui/README.md에 <...>가 남지 않았고 패키지 이름·props·컴포넌트 목록이 실제 코드와 같은지, handoff/my-ui-0.1.0.tgz가 생겼는지
      삭제 전 삭제 대상이 consumer/dist와 consumer/node_modules/my-ui뿐인지
      체크리스트 check.mjs 세 항목이 PASS인지, SAME이 두 번인지, 정의되지 않은 CSS 변수와 직접 입력한 색상 값의 검색 결과가 없는지, 새 패키지로 consumer가 빌드되는지

    2. 기대 결과: 0.1.0 전달 묶음이 검사를 통과합니다.

    3. 확인 방법: 검사 명령은 Codex의 요약이 아니라 출력으로 확인합니다. 색상 값 검색은 결과가 없으면 종료 코드 1이 나오며 정상입니다.

    5-3. 색상 변경 요청¶

    디자이너가 3B82F6인 파란색을 더 진한 2563EB로 바꾼 상황입니다. 이 색은 Button 배경과 Input의 focus 선에 쓰이므로 두 컴포넌트에서 변경을 확인할 수 있습니다. 변경은 매번 내용이 다르므로 skill로 만들지 않고, 요청을 프롬프트에 적어 Codex가 skill 4개를 참고해 절차를 만들게 합니다.

    1. 작업: Figma 사본에서 값이 3B82F6인 원시 색상 변수를 2563EB로 직접 바꾼 뒤, 아래 프롬프트를 보냅니다.

      프롬프트
      1
      Figma 사본의 #3B82F6 색상 변수를 #2563EB로 바꿨어. .agents skill 규칙대로 전달 묶음까지 0.1.1로 반영하되, 계획부터 보여줘.

    2. 기대 결과: Codex가 계획을 보여주고 승인을 기다립니다. 계획은 실행할 때마다 다를 수 있습니다.

    3. 확인 방법: 아래 항목이 계획에 모두 있으면 승인이라고 답합니다. 프롬프트가 짧아 빠질 수 있으므로, 빠진 항목은 적어 보냅니다.

      확인할 것 기준
      순서 Figma의 값 확인 → ds-spec.json → 토큰과 CSS 변수 → my-ui → handoff → consumer
      승인 지점 단계가 끝날 때, 파일이나 폴더를 삭제하기 전에 멈춥니다.
      검사 check.mjs와 ds-handoff의 체크리스트를 다시 실행합니다.
      수정 범위 ds-spec.json에서는 바꾼 변수의 값만 바뀌고, 컴포넌트 코드와 .agents는 바뀌지 않습니다.
      기록 버전은 0.1.1이고 CHANGELOG.md에 이전 값과 새 값을 남깁니다. 배포와 외부 전송은 하지 않습니다.

    4. 2-3에서 두 위치를 서로 다른 원시 변수에 연결했다면 바뀌는 위치가 다를 수 있습니다.

    5-4. 새 버전 승인¶

    1. 작업: Codex가 멈출 때마다 명령 출력을 확인하고 승인이라고 답합니다. CSS 변수가 갱신된 단계에서는 CSS 차이도 확인합니다.

    2. 기대 결과: 아래 항목이 모두 맞습니다.

      항목 통과 기준
      CSS 차이 이전 handoff/tokens/variables.css와 비교해 바꾼 변수 한 줄만 다릅니다. diff의 종료 코드 1은 정상입니다.
      검사 check.mjs 세 항목이 PASS입니다.
      버전과 변경 이력 버전이 0.1.1이고, CHANGELOG.md의 이전 값과 새 값이 실제 차이와 같습니다.
      패키지 consumer에 0.1.1을 설치해 타입 검사와 빌드가 되고, 빌드한 CSS의 해당 변수에는 새 값만 있습니다.
      전달 폴더 handoff/tokens의 파일이 새 값으로 갱신돼 있습니다.

    3. 확인 방법: 터미널에서 전달 폴더를 직접 확인합니다.

      실행 위치: design-system-practice-auto

      명령어

      1
      ls handoff handoff/tokens && grep -i '2563eb' handoff/tokens/variables.css

      출력 결과: handoff에 my-ui-0.1.1.tgz와 tokens가, handoff/tokens에 tokens.json과 variables.css가 있습니다. 0.1.0 패키지도 함께 남아 있을 수 있습니다. 마지막에는 새 값이 있는 CSS 변수 한 줄이 나옵니다. 변수 이름은 설계에 따라 다릅니다.

    6-3. 한계와 검토 방법¶

    한계 검토 방법
    Codex의 완료 보고만으로는 통과 여부를 알 수 없습니다. 검사 명령은 출력까지 확인합니다.
    승인 규칙을 지키지 않고 다음 작업을 실행할 수 있습니다. 원본이 아닌 Figma 사본과 자동화 폴더에서만 실행하고, 승인 없이 진행하면 중단합니다.
    검사는 ds-spec.json과 같은지만 확인합니다. ds-spec.json이 틀리면 이후 검사도 통과합니다. 설계안과 ds-spec.json을 승인할 때 원본 파일의 값·연결 위치와 직접 비교합니다.
    결과가 실행할 때마다 다를 수 있습니다. 이름이 아니라 값과 겉모습을 원본과 비교합니다.
    화면 모양은 명령 결과로 판정할 수 없습니다. Figma와 Storybook 화면을 사람이 확인합니다.

    막혔을 때¶

    증상 확인
    use_figma가 없거나 권한 오류가 남 요금제, 파일 편집 권한, 원격 서버 연결을 확인하고, 해결되지 않으면 실습을 건너뜁니다.
    skill 목록에 ds- skill이 없음 작업 폴더가 design-system-practice-auto인지, 1-4의 폴더 4개가 있는지 확인합니다.
    ds-spec.json, my-ui, consumer, handoff가 이미 있어 멈춤 이전 실행의 결과입니다. 이어서 쓸지 확인하고, 처음부터 하려면 새 작업 폴더와 새 Figma 사본을 만듭니다.
    다음 skill이 시작하지 않고 앞 단계의 skill을 안내함 앞 단계의 산출물이 있는지, ds-spec.json의 status가 confirmed인지 확인합니다.
    검사 결과가 FAIL임 출력의 없음:, 다름·추가: 줄을 보고 Figma와 ds-spec.json 중 어느 쪽이 맞는지 정한 뒤 Codex에 알립니다.
    Codex가 승인 없이 다음 작업을 실행함 중단하고 바뀐 내용을 확인합니다. Figma가 의도와 다르게 바뀌었으면 원본에서 새 사본을 만들어 다시 시작합니다.
    대화가 끊겨 새 대화를 시작함 작업 폴더를 다시 열고, 진행하던 skill의 이름과 마지막으로 승인한 지점을 적어 보냅니다. 산출물을 확인하게 한 뒤 이어 갑니다.
    Figma 도구 호출이 실패함 오류 메시지, Figma 접근 허용 여부, 파일 접근 권한, 호출 제한을 확인합니다.
