# 파드와 그 구성 요소

[← Kubernetes로 돌아가기](index.md)

Pod는 쿠버네티스가 생성·삭제·이동을 관리하는 가장 작은 배포 단위입니다([쿠버네티스 개요](overview.md) 참고). 이 문서에서는 Pod를 이해하는 데 필요한 세 가지, Container·Label·스케줄링을 하나씩 살펴봅니다.

| 개념 | 설명 |
|---|---|
| Container | Pod 안에서 실제로 애플리케이션이 실행되는 단위 |
| Label | Pod를 구분하고 선택하기 위해 붙이는 key=value 이름표 |
| 스케줄링 | Pod를 어떤 Node에 배치할지 결정하는 과정 |

---

## Pod는 보통 Container 하나를 담는 배포 단위입니다

대부분의 Pod는 Container를 하나만 담습니다. 애플리케이션 하나에 Container 하나를 대응시키는 것이 가장 단순하고 관리하기 쉽기 때문입니다. 하지만 로그 수집기나 프록시처럼, 메인 애플리케이션과 항상 같은 위치에서, 생성될 때 같이 떠서 삭제될 때 같이 내려가야 하는 보조 역할이 있다면 이런 Container들을 하나의 Pod에 함께 담습니다. 같은 Pod 안의 Container들은 네트워크와 저장 공간을 공유하기 때문에, 서로 `localhost`로 통신할 수 있고 항상 같은 Node에서 함께 뜨고 함께 내려갑니다.

→ **Pod는 Container를 담는 그릇이며, 특별히 함께 묶여야 할 이유가 없다면 Container 하나당 Pod 하나로 구성하는 것이 기본입니다.**

## Label은 Pod를 구분하고 선택하는 이름표입니다

Pod가 많아지면 어떤 Pod가 어떤 역할인지 이름만으로는 구분하기 어렵습니다. 게다가 Pod는 문제가 생기면 같은 자리에서 재시작되는 게 아니라 통째로 삭제되고 새로 만들어지며, 그때마다 IP 같은 접속 정보도 바뀝니다.

그래서 특정 Pod를 IP나 이름으로 고정해서 찾기보다는, Label이라는 이름표를 기준으로 찾는 방식을 씁니다. Label은 `app=api`, `env=production`처럼 key=value 형태로 Pod에 붙이며, 하나의 Pod에 여러 개를 동시에 붙일 수 있습니다.

쿠버네티스의 다른 구성 요소들은 이 Label을 기준으로 원하는 Pod 묶음을 골라냅니다. 예를 들어 [쿠버네티스를 사용하는 이유](why.md)에서 설명하는 고정된 접속 창구가 트래픽을 전달할 Pod를 고를 때도, 특정 Pod 그룹을 한꺼번에 관리할 때도 Label을 기준으로 삼습니다.

→ **Label은 Pod에 붙이는 검색용 이름표이며, 쿠버네티스는 이 이름표를 기준으로 원하는 Pod 묶음을 선택합니다.**

## 스케줄링은 Pod가 어떤 Node에 배치될지 결정합니다

새 Pod가 만들어지면 쿠버네티스는 이 Pod를 어느 Node에서 실행할지 자동으로 결정해야 합니다. 여러 개의 빈 방 중에서 손님 조건에 맞는 방을 골라 배정하는 것과 비슷하게, 각 Node의 남은 자원(CPU, 메모리 등)과 Pod가 요구하는 조건을 비교해서 가장 적절한 Node를 골라 배치합니다. 이 배치를 담당하는 내부 구성 요소를 스케줄러라고 부릅니다. 지금은 스케줄러가 이 역할을 맡고 있다는 정도만 알아두면 충분합니다. 특정 Node에만 배치되도록 조건을 지정할 수도 있지만, 대부분의 경우에는 스케줄러가 알아서 적절한 자리를 찾아줍니다.

→ **스케줄링은 스케줄러가 Node의 자원 상황을 보고 Pod를 배치할 자리를 자동으로 결정하는 과정입니다.**
