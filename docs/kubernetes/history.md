# 쿠버네티스의 역사

[← Kubernetes로 돌아가기](index.md)

쿠버네티스는 어느 날 갑자기 등장한 기술이 아니라, 자원 격리 → 가상화 → 컨테이너 → 오케스트레이션으로 이어지는 흐름 속에서 탄생했습니다. 이 문서에서는 세 가지, 자원 격리·가상화·컨테이너 오케스트레이션을 하나씩 살펴봅니다.

![쿠버네티스에 이르는 흐름](../assets/images/kubernetes/history.svg){ width="100%" }

| 개념 | 설명 |
|---|---|
| 자원 격리 | 리눅스 커널이 프로세스 단위로 자원을 나누는 기반 기술 (1991) |
| 가상화 | 하이퍼바이저로 서버 한 대 안에 여러 운영체제를 띄우는 기술 (2010.7) |
| 컨테이너 오케스트레이션 | 컨테이너를 여러 서버에 걸쳐 자동으로 관리하는 기술 (2014.6~) |

---

## 자원 격리는 컨테이너 기술의 토대가 되었습니다

1991년 등장한 리눅스 커널의 `chroot`, `namespace`, `cgroup` 기능은 하나의 서버 안에서 프로세스마다 파일·네트워크·자원 사용량을 나눠 격리하는 기반 기술입니다. 이때는 아직 컨테이너라는 개념이 없었지만, 이후 등장하는 컨테이너 기술은 모두 이 자원 격리 기능 위에서 만들어집니다.

→ **리눅스의 자원 격리 기능은 이후 컨테이너 기술이 만들어지는 토대가 되었습니다.**

## 가상화는 서버 한 대 안에 여러 운영체제를 띄웠습니다

2010년 7월을 전후로 VirtualBox, VMware, KVM, Xen 등 하이퍼바이저 기반 가상화 기술이 널리 쓰이기 시작했습니다. [VM과 Container의 차이](vm-vs-container.md)에서 다루는 것처럼, VM은 서버 한 대 안에 운영체제를 통째로 여러 개 띄워 프로그램을 격리합니다. Rackspace와 NASA가 공동 개발한 OpenStack은 이런 가상 인프라를 관리하는 클라우드 플랫폼으로 등장했습니다.

→ **가상화는 운영체제 단위로 서버를 나눠 쓸 수 있게 했지만, 운영체제를 통째로 띄우는 만큼 무겁고 느렸습니다.**

## 컨테이너 오케스트레이션은 여러 서버에 걸친 관리를 자동화했습니다

2014년 6월, dotCloud 사는 커널을 공유하는 가벼운 컨테이너 방식의 Docker를 공개했습니다. 무거운 VM을 대신할 가상화 기술로 주목받았지만, 컨테이너 수가 늘어나자 이번엔 여러 서버에 걸쳐 컨테이너를 관리·배포·확장하는 오케스트레이션 도구가 필요해졌습니다. 2015년 7월을 전후로 이 영역에서 Docker Swarm, Amazon ECS, Rancher, HashiCorp Nomad 등이 경쟁했습니다.

이 경쟁 속에서 Google이 자사의 내부 컨테이너 관리 시스템(Borg) 경험을 바탕으로 2015년 7월 쿠버네티스 v1.0을 릴리스했습니다. 이후 Red Hat, Microsoft, IBM, CoreOS, Docker, Mesosphere, SaltStack 등이 참여하는 커뮤니티가 형성되었고, Google Cloud·AWS·Azure·IBM Cloud·Oracle Cloud 같은 주요 클라우드 사업자들도 쿠버네티스를 관리형 서비스로 제공하기 시작했습니다.

→ **컨테이너가 늘어나며 필요해진 오케스트레이션 경쟁 속에서, 쿠버네티스가 여러 기업과 클라우드의 지지를 받아 사실상 표준 도구로 자리잡았습니다.**

## 세 흐름은 결국 쿠버네티스로 이어집니다

자원 격리가 컨테이너 기술의 토대를 놓았고, 가상화는 서버를 나눠 쓰는 방법을 먼저 보여줬지만 무겁고 느렸습니다. 그 자리를 가벼운 컨테이너가 대신하자, 늘어난 컨테이너를 관리할 오케스트레이션 도구가 필요해졌고, 그 경쟁에서 쿠버네티스가 사실상 표준으로 자리잡았습니다.

→ **쿠버네티스는 자원 격리 → 가상화 → 컨테이너 → 오케스트레이션으로 이어지는 흐름의 결과물이며, 지금은 컨테이너 오케스트레이션의 사실상 표준입니다.**
