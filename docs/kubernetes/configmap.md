# ConfigMap과 설정 관리

[← Kubernetes로 돌아가기](index.md)

애플리케이션의 설정 값(DB 주소, 로그 레벨 등)을 코드 안에 직접 적어두면, 환경이 바뀔 때마다 이미지를 새로 빌드해야 합니다. ConfigMap은 이런 설정 값을 Key-Value 형태로 따로 관리해, 애플리케이션 코드와 설정을 분리하기 위한 리소스입니다. 이 문서에서는 네 가지, ConfigMap·Secret·Env·Mount를 하나씩 살펴봅니다.

| 개념 | 설명 |
|---|---|
| ConfigMap | 일반 설정 값을 Key-Value 형태로 저장하는 리소스 |
| Secret | 비밀번호, 인증서 같은 민감한 값을 저장하는 리소스 |
| Env | 저장된 값을 Container의 환경변수로 주입하는 방식 |
| Mount | 저장된 값을 Container 내부 파일로 주입하는 방식 |

---

## ConfigMap은 설정 값을 코드와 분리해서 관리합니다

ConfigMap은 `key: value` 형태의 설정 값을 담는 쿠버네티스 리소스입니다. DB 주소나 로그 레벨처럼 환경(개발·운영 등)에 따라 달라지는 값을 ConfigMap에 담아두면, Container 이미지는 그대로 두고 ConfigMap만 바꿔서 환경별로 다른 설정을 적용할 수 있습니다.

예를 들어 `DB_HOST`라는 값 하나를 `app-config`라는 이름의 ConfigMap에 담아둘 수 있습니다. 이렇게 만든 ConfigMap은 그 자체로는 아무 역할도 하지 않고, 뒤에서 살펴볼 Env나 Mount 방식을 통해 Pod에 연결해야 실제로 사용할 수 있습니다.

→ **ConfigMap은 설정 값을 코드와 분리해서 관리하는 리소스이며, 이미지를 새로 빌드하지 않고도 환경별로 다른 설정을 적용할 수 있게 해줍니다.**

## Secret은 민감한 값을 다루는 ConfigMap과 유사한 리소스입니다

ConfigMap은 값을 평문으로 저장하기 때문에, DB 비밀번호나 API Key, 인증서처럼 노출되면 안 되는 값을 담기에는 적합하지 않습니다. Secret은 이런 민감한 값을 다루기 위해 별도로 만들어진 리소스로, 사용하는 방식(Env·Mount)은 ConfigMap과 동일합니다.

다만 Secret도 기본적으로는 값을 base64로 인코딩해서 저장할 뿐 암호화하지는 않습니다. base64는 누구나 바로 원래 값으로 되돌릴 수 있는 형식이라, 그 자체로 완전한 보안을 보장하지는 않습니다. 그래서 실제 운영 환경에서는 클러스터 접근 권한을 제한하거나, 외부 비밀 관리 도구와 연동하는 방식을 함께 사용합니다.

→ **Secret은 민감한 값을 다루기 위한 ConfigMap과 유사한 리소스이며, 사용 방식은 같지만 접근 권한 관리가 별도로 필요합니다.**

## Env는 설정 값을 환경변수로 주입하는 방식입니다

Env 방식은 ConfigMap이나 Secret에 저장된 값을 Container의 환경변수로 전달합니다. 앞서 만든 `app-config`의 `DB_HOST` 값을 Pod의 환경변수로 연결하면, 애플리케이션은 평소 환경변수를 읽는 방식 그대로 설정 값을 사용할 수 있어, 별도의 파일 처리 로직 없이 간단하게 값을 주입할 수 있습니다.

다만 환경변수는 Container가 이미 실행 중일 때 값이 바뀌어도 다시 읽어들이지 않기 때문에, ConfigMap이나 Secret의 값을 수정해도 실행 중인 Container에는 반영되지 않습니다. 값을 반영하려면 Pod를 재시작해야 합니다.

→ **Env는 설정 값을 환경변수로 주입하는 방식이며, 간단하지만 값이 바뀌어도 Pod를 재시작해야 반영됩니다.**

## Mount는 설정 값을 파일로 주입하는 방식입니다

Mount 방식은 ConfigMap이나 Secret에 저장된 값을 [Volume](volume.md)처럼 Container 내부의 특정 경로에 파일로 연결합니다. 각 Key는 파일 이름이 되고 Value는 그 파일의 내용이 되어, 애플리케이션은 설정 파일을 읽듯이 이 값을 사용할 수 있습니다. 같은 `app-config`를 마운트하면 Container 안에는 `/etc/config/DB_HOST`라는 파일이 생기고, 그 안에 `db.example.com`이라는 내용이 담깁니다.

Env 방식과 달리 ConfigMap이나 Secret의 값이 바뀌면 마운트된 파일의 내용도 자동으로 갱신됩니다. 다만 애플리케이션이 파일 변경을 감지해서 다시 읽어들이는 로직을 직접 구현하지 않는 한, 이미 메모리에 올려둔 값은 바뀌지 않습니다. 그래서 설정 파일 전체를 통째로 주입해야 하거나, 값이 자주 바뀌는 경우에 주로 사용합니다.

→ **Mount는 설정 값을 파일로 주입하는 방식이며, 값이 바뀌면 파일은 자동으로 갱신되지만 애플리케이션이 이를 다시 읽어야 반영됩니다.**

## Env와 Mount, 어떤 방식을 선택해야 할까요

두 방식 모두 같은 ConfigMap·Secret을 사용할 수 있지만 특성이 다릅니다. 값 몇 개를 간단히 전달하고, 값이 자주 바뀌지 않는다면 Env가 다루기 쉽습니다. 반대로 설정 파일 전체를 통째로 넘겨야 하거나, Pod를 재시작하지 않고도 값 변경을 반영하고 싶다면 Mount가 적합합니다.

→ **값이 적고 단순하면 Env를, 파일 전체가 필요하거나 값이 자주 바뀌면 Mount를 선택합니다.**
